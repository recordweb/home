RecordWeb Protocol (RWP) · Quick'n'Dirty

Was ein RWP-Record wirklich ist - und wie man ihn findet.

Sieben Bausteine: von der Identität eines Datensatzes über seinen Inhalt und seine Integritätssicherung bis zur Auflösungs-Infrastruktur, die aus einer DID einen erreichbaren Datensatz macht.

1 Identität Die DID

Jeder Record besitzt eine stabile, dezentrale Identität. Der namespace verweist auf eine Organisation/Infrastruktur, die record-id ist innerhalb dieses Namensraums eindeutig. Optionale Segmente adressieren gezielt einzelne Versionen oder Repräsentationen.

// Aufbau der DID did:rwp:<namespace>:<record-id> [:<versionHash>][:<contentHash>] // Beispiel did:rwp:5264d2c3-…:f47ac10b-…
2 Container Der Record

Der Record selbst ist ein schlankes Hüllobjekt: eine DID, ein Payload mit dem Lebenszyklus der Inhalte, Metadaten zur Einordnung und ein Hash, der alles kryptographisch verklammert.

{ "did": "did:rwp:5264d2c3-…:f47ac10b-…", "payload": [], "metadata": {}, "recordHash": "sha256:9f8e7d…" }
3 Inhalt Payload

Der Payload ist eine Liste von Versions-Snapshots (Draft → finalized), jeweils mit Eltern-Verweisen, Signatur und einer oder mehreren representations - dem eigentlichen Inhalt in verschiedenen Formaten, inline oder per Referenz.

{ "payload": [{ "versionHash": "sha256:eef9dd…", "state": "finalized", "parents": ["sha256:6ce834…"], "signature": "z3FttV7…", "representations": [ { "format": "text/markdown", "content": "sample text", "contentHash": "sha256:3a84b2…", "primary": true, "role": "source" }, { "format": "application/pdf;…", "ref": "sample reference", "primary": false, "role": "publication" } ]}]}
4 Einordnung Metadaten

Drei Ebenen: core (Typ und Schema-Version als eigene RWP-Records), governance (Owner, Klassifizierung, Aufbewahrung, Tags) und optionale extensions für domänenspezifische Erweiterungen.

{ "metadata": { "core": { "recordType": "did:rwp:2fe146…:5264d2…", "schemaVersion": "sha256:a665a4…" }, "governance": { "owner": "did:rwp:bern.ch:unit-baubewilligung", "classification": "internal", "retentionPolicy": "did:rwp:bern.ch:retention-bauakten-30y", "tags": ["building-permit", "parcel-451"] }, "extensions": [] }}
5 Integrität recordHash

Der Hash verklammert did, payload und metadata kryptographisch - jede Änderung an einem der drei Felder verändert den Hash. versionHash und contentHash werden sinngemäss über die jeweiligen Versions- bzw. Representation-Felder berechnet.

// Canonical JSON (RFC 8785) + SHA-256 recordHash = SHA-256( canonicalize({did, payload, metadata}) ) // analog für einzelne Snapshots // und Representations
6 Auflösung DID-Dokument

Pro DID existiert ein DID-Dokument mit recordEndpoint (der festen URL, unter der der eigentliche Record ausgeliefert wird) sowie Verwaltungsangaben wie Controller und Verification Methods.

{ "id": "did:rwp:5264d2c3-…:f47ac10b-…", "recordEndpoint": "https://records.bern.ch/api/v1/…", "currentVersion": "sha256:e3b0c4…", "controller": "did:rwp:bern.ch:controller-001" }
7 Auflösung Global Namespace Registry

Der Namensraum selbst wird zentral (DLT-gestützt) im GNR registriert und zeigt auf den resolverEndpoint, die Organisation, die für alle Records dieses Namensraums DID-Dokumente ausliefert.

{ "docType": "namespaceRecord", "namespace": "5264d2c3-…", "resolverEndpoint": "https://vps.recordweb.dev/resolver/…", "registeredBy": "SwissGovOrgMSP", "endorsedBy": ["SwissGovOrgMSP"] }
