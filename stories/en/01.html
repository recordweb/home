Welcome. This story explains RecordWeb through a situation many people know from administrative work: an answer must be delivered reliably and on time, while the next task is already waiting.

Ms. Roth has only a few minutes left.

She works in a government office on the answer to a request from parliament. The figures are almost verified. The answer needs to be approved.

Scene 3 · The question becomes a mandate

Mr. Keller submits the question formally.

Now the matter gets a clear reference: who is asking which question, at what point in time — and who is responsible for the answer?

A formal question should not only be answered correctly. It should be handled on time and, above all, traceably.
This is where the Question Time PoC starts: the submission of a member of parliament's question. In practice this process is quite complex; for demonstrating RecordWeb a strong simplification is sufficient.

Reality: Ms. Roth must deliver a factually correct and timely answer, while already taking on the next task in parallel.

This is the core of today's business-management-system problem. The problem is not that Ms. Roth doesn't want order. She must fulfil several obligations at the same time. Her immediate responsibility is the correct and timely answer.

The binding answer does not come from a single person, and not from a single place.

It emerges from subject-matter expertise, sources, follow-up questions, drafts, and shared consensus.

The chat is not a disruptive side channel. It is an actual place of work.
In the Question Time PoC, MiniChat likewise represents — in a strongly simplified way — any communication. What matters is not the individual message but the connection: this chat room belongs to this question; the participants are working on this answer; at the end there is a coordinated result. But how is it linked and persisted?

Scene 6 · The trade-off

The answer is the goal. The follow-up documentation comes afterwards.

The additional work

  • Select and export the chat history
  • Save emails and attachments
  • File and classify documents
  • Retroactively assess relevance and completeness
  • Convert and close the case

The actual work

  • Check the figures
  • Bring subject-matter expertise together
  • Find a sound formulation
  • Take responsibility
  • Deliver the answer on time
Not because follow-up documentation is unimportant. But because the next question is already waiting.
This slide is not meant to devalue records management. Orderly, complete record-keeping is a legitimate and important goal. The tension arises where manually transferring the actual work into a system competes with deadlines, interruptions, and parallel tasks.

Scene 7 · A different path

RecordWeb starts with work as it actually happens.

RecordWeb does not require Ms. Roth to do her work twice: once for the answer and once for its traceable documentation.

QuestionMr. Keller asks a formal question.
→
CollaborationThe subject-matter team reviews, discusses, and aligns.
→
AnswerAn accountable, approved answer is delivered.

RecordWeb: The relevant outcomes, responsibilities, and relationships can stay connected while the work happens.

The message is simple: not a final document without provenance, but a traceable connection between question, work, and answer.

Scene 8 · The bridge

The chat doesn't need to be replaced.

Existing chat and business applications can't yet speak RWP. RecordWeb doesn't demand an immediate system change.

Existing chatMs. Roth and her team work in their familiar tool.
→
SoXAn integration layer establishes the link to RecordWeb
→
RecordWebReferenceable and traceable information.
SoX doesn't replace the working application. SoX creates the connection.
SoX = "System of X" — in principle an adapter layer to another system, SoW, SoR, or others. Important: SoX is not an additional storage machine into which Ms. Roth copies everything. It's the bridge that gradually connects the existing application to the RecordWeb environment. SoX has no user interface for staff.

Outlook

RecordWeb doesn't start with a system change.

Existing applications can keep working as they are.

New or soon-to-be-replaced applications can gradually become interoperable.

Over time, this creates an information architecture in which relevant context is preserved.

This is not a big bang. It is a long-term architectural decision.

This outlook is deliberately kept brief. Topics such as procurement, conformance, application end-of-life, migration to successor systems, or archiving get their own stories.
