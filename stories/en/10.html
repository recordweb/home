RecordWeb · Discoverability across change

Where is this record?

The name stays. The location can change.

Don't search for the old location.
Resolve the stable name.
This presentation has two parts. Part one starts with Ms. Berger and explains, without requiring technical background, why a record must stay discoverable across change. Part two shows the concrete resolution path for a technical audience: DID, namespace, root resolver, DID document, and RecordEndpoint.

Part 1 · The story of a search

Ms. Berger is looking for an answer she once found before.

Some years after the question-time session, journalist Ms. Berger wants to refer once more to the earlier answer on the trend in CO₂ emissions.

She has an old link saved. She clicks it.

FB

Ms. BergerJournalist, later user

"I know this answer exists. But where do I find it today?"

The starting situation is deliberately human and everyday. It connects to the presentation "The answer explains itself." This time, however, the focus isn't primarily on the context of a found answer, but on the preceding question: how does Ms. Berger find the record again at all, once systems have changed?

Scene 1 · The old location

The saved link leads nowhere.

https://old-system.example.gov/answers/co2-2026
404Page not foundThe application was retired. The former web address no longer exists.

The information may still exist. But its former address described a location that has changed — server, domain, application, or area of responsibility.

The 404 slide is deliberately emotional. But it shouldn't unfairly disparage URLs — URLs can be maintained permanently, redirected, or embedded in PID systems. The claim is narrower: a URL contains a specific hosting location. If that changes, the address must be actively maintained. RecordWeb therefore separates the permanent name of the record from its current endpoint.

Scene 2 · Separating name and location

A URL is an address. A DID is a stable reference point.

Web address

  • Contains domain, server, and path
  • Describes where something is available today
  • Must be actively updated when systems, domains, or structures change
  • Can lead to a 404 page if not maintained

RecordWeb DID

  • Names exactly this record
  • Contains no current server and no domain
  • Is resolved via a registry and resolver
  • Can lead to the current endpoint when the location changes
The name says: this is this record.
Resolution finds out: where is it provided today?
The term DID can be introduced here — decentralized identifier. For the audience, the separation between identity and location matters more than the abbreviation. Ultimately, the DID is the reason a record can stay referenceable across system retirements and custodyTransfers.

Scene 3 · The stable name

The DID names the record without speculating about it.

did:rwp:b7d4c810:2fe14680-575a-4da4-aa65-6e72e0866e9b
did:rwp:

The marker: this identifier follows the RecordWeb method.

b7d4c810

Opaque namespace. It leads to the accountable resolution information.

2fe14680-575a-4da4-aa65-6e72e0866e9b

Opaque and technically unique string (UUID). It reveals neither topic, RecordType, organisation, nor current location.

The DID is implemented as did:rwp:namespace:uuid. The RecordType only becomes visible when the record is retrieved.

Scene 4 · Why the identifier doesn't speak

A stable name shouldn't encode a changeable assumption.

A descriptive name would lock in

  • which organisation is responsible
  • which topic or classification applies
  • which RecordType is expected
  • which language, structure, or domain is used

An opaque identifier only says

  • this is exactly this record
  • the location can change later
  • responsibility can transfer
  • type and context are determined from the record itself
Opaque does not mean secret. It means: the permanent name stays neutral toward change.
An opaque identifier alone doesn't prevent a 404 page. But it does prevent the permanent identity from being directly coupled to a changeable endpoint, an organisation name, or a business structure. For resolution to keep working permanently, a registry, resolver, and governance are also needed.

Scene 5 · The namespace as a resolution space

The namespace doesn't answer "what is this?" but "who knows how to resolve it?"

A namespace bundles a mapping to a resolver. How finely or broadly it is cut is an organisational and governance decision, not a requirement of the protocol.

Namespace designPossible strengthPossible consequence
Per organisationSimple entry point, few responsibilitiesChanges can affect a large area
Per applicationClear technical operating boundaryMore namespaces and more transitions at end of life
Per business or accountability areaCan follow stable tasks and custody structuresRequires clear business governance
Fine-grained custody areasTargeted and smaller custodyTransfers possibleMore administrative and decision-making effort
Important: RWP makes no recommendation. This slide makes visible that namespace strategy is an enormously important adoption and governance topic. A namespace strategy is very hard to change after the fact. Organisations also need to decide which unit is accountable for the resolver and how this responsibility can sensibly continue through custodyTransfers.

Scene 6 · An established principle

A resolver is a signpost.

Many people know the principle from DNS: a name is resolved so that a technical target can be found.

RecordWeb follows the same basic idea, with one extra step: the resolver doesn't just return a technical address, but a DID document with the current RecordEndpoint and further information about the record.

?

Resolverfinds the accountable path to the record

Simple picture: DNS helps find a domain name. A RecordWeb resolver helps find a record via its DID and namespace.

Don't dwell too long on DNS. It's merely a familiar image: resolution is not an exotic idea. The difference is that RecordWeb first finds the namespace resolver, then retrieves the DID document, and finally uses its RecordEndpoint.

The DID doesn't need to reveal a type. The recordType in the retrieved record makes visible what kind of record this is. Status, ownership, and schema/version references can also be checked.

This completes the technical flow. After retrieval, the RecordFinder shows a human-readable view: payload, record details, and technical metadata. This display illustrates that discoverability and authorisation must be treated separately.

Note: in this example, the RecordType is not yet opaque. With the correct DID, a SchemaRecord can also be read at any time via a RecordFinder.

Technical evidence · When the location changes

At custodyTransfer, the endpoint changes, not the identity.

Old applicationProvides the record today via its endpoint.
→
custodyTransferResponsibility and provision continue in a controlled way.
→
Successor application or AISProvides the same record via a new accountable endpoint.
Ms. Berger doesn't need to learn a new link. She resolves the same DID again and gets the current path to the record.
This slide connects the discoverability story with the archival story. At end of life, a successor specialist application or an AIS can take over provision. The concrete RecordEndpoint changes — the DID remains the reference. This deliberately separates the name from the current location.

Technical appendix · Long-term governance

A globally resolvable registry needs long-term, shared responsibility.

Today: PoC testnet

Hyperledger Fabric 2.5 as a permissioned blockchain. The testnet contains 3 sample organisations and one channel, root-resolver.

It demonstrates the technical and organisational idea of a multilaterally endorsed namespace registration.

Discussion picture for later

An international RecordWeb steward organisation could be responsible for specification, governance, and initial operation of the root registry.

Member authorities could gradually take on infrastructure and shared responsibility, so that operation and governance become increasingly federated.

Framing: the picture on the right is a development hypothesis, not an already existing organisation or a production commitment.
Here the vision should be clearly labelled as such — for example an internationally oriented steward organisation modelled on a standards-maintaining community, with membership of national authorities. At minimum, it would initially secure registry governance. As participation grows, peers and orderers could be distributed among members. Important: the steward organisation should not necessarily have to operate infrastructure alone long-term, but should secure specification and governance.

Technical appendix · A possible development path

From initial operation to a federated trust foundation.

1Start

A steward organisation establishes specification, policies, and an initial registry operation.

2Participation

National or sectoral authorities join, bringing requirements, legitimacy, and governance.

3Distribution

Members can co-support infrastructure; the registry becomes technically and organisationally more robust.

4Maturity

The steward organisation increasingly focuses on specification, interoperability, and governance.

The blockchain is not the story. It's one possible mechanism so that the mapping "namespace → resolver" doesn't depend on a single, changing website.
This slide answers the "why blockchain?" question. It's about a shared, verifiable, and federally governed root registry. Hyperledger Fabric is the chosen permissioned technology in the PoC. RWP can refine the registry architecture further later — as of now it is not yet reflected in the protocol.
